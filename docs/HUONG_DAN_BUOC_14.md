# CyberSentinel - Buoc 14: HTTPS Staging Ingest Bridge

## Muc tieu

Step 14 delivers a **limited staging path for external agents**. It does not launch an open registration portal or production SaaS. The core trust boundary is:

- An external NGINX agent sends only minimized telemetry over a certificate-validated HTTPS origin.
- Caddy on your own VPS exposes exactly `POST /agent/v1/ingest` on a dedicated hostname.
- Caddy forwards to `owner_api.ingest_only` at `127.0.0.1:8004`. This ASGI app does not contain account endpoints or OpenAPI docs.
- The separate private Owner API stays on `127.0.0.1:8002`, reachable through an administrator-controlled SSH tunnel, not the public reverse proxy.
- Both processes share one local SQLite database (staging only). Alerts are generated by the existing Step 12 rules.

Do not put the Owner Portal or full Owner API on the public Internet. Do not claim this is production-ready.

## 14.2 Test separate API locally (no VPS required)

Terminal A - private Owner API:

```bash
uvicorn owner_api.main:app --host 127.0.0.1 --port 8002
```

Terminal B - ingest-only API:

```bash
uvicorn owner_api.ingest_only:app --host 127.0.0.1 --port 8004
```

These processes use the same ignored SQLite database. Test the second API:

```bash
curl --noproxy '*' -i http://127.0.0.1:8004/docs
curl --noproxy '*' -i http://127.0.0.1:8004/owner/health
curl --noproxy '*' -i http://127.0.0.1:8004/owner/register
```

All three must return `404`. This proves that the isolated process does not expose owner routes. To test a real agent ingest, use the locally issued domain ID and agent key from Step 11 or run the unit tests. Port 8004 is local-only even in this test.

## 14.3 Optional staging on a private VPS

This section requires your own VPS, DNS hostname, SSH access, HTTPS-capable reverse proxy, and backups. The commands are **examples**, not an automatic cloud deployment. Do not execute this section just to pass Step 14 unit tests.

1. Create a dedicated non-root Linux service account named `cybersentinel`. Place a clean checkout in `/opt/cybersentinel/app` and a Python virtual environment in `/opt/cybersentinel/venv`. Grant the service account read access to source files, and create `/var/lib/cybersentinel` owned by that account, mode `0700`.
2. Install dependencies from `requirements-dashboard.txt`, `requirements-owner.txt` and the editable package. Keep the service behind a firewall. Never expose ports 8002 or 8004; only allow SSH from trusted sources and ports 80/443 for Caddy.
3. Review and adapt `deploy/cybersentinel-owner.service.example` and `deploy/cybersentinel-ingest.service.example`. Both use `CYBERSENTINEL_OWNER_DB=/var/lib/cybersentinel/owner.sqlite3`. Install as systemd services after reviewing paths, permissions, security settings and user/group.
4. Set a DNS A/AAAA record for a hostname such as `ingest.your-domain.com`, pointing to the VPS. Use **Caddy 2.10+**. Merge `deploy/Caddyfile.ingest.example` into your existing Caddy configuration, replacing `{$INGEST_HOST}` with your actual public hostname or setting the `INGEST_HOST` environment variable for Caddy's systemd unit. Do not replace an existing Caddy config without reviewing it.
5. Before starting the public listener, run `caddy validate --config /path/to/Caddyfile --adapter caddyfile`, then inspect your firewall and verify the proxy forwards to `127.0.0.1:8004`, not 8002. Confirm a publicly trusted TLS certificate is issued and certificate hostname validation succeeds. Do **not** disable TLS verification.
6. For administrator onboarding, create an SSH tunnel on your laptop: `ssh -N -L 8002:127.0.0.1:8002 your-user@your-vps`. Run the Owner Portal **locally on your laptop**, where it can reach `http://127.0.0.1:8002` through that tunnel. The portal must not be directly served by Caddy.
7. Through the private Owner Portal, register a staging account, DNS-verify a domain you control and issue a **staging** agent API key. Store the key in a local environment variable only.
8. On a different machine you control, install the agent package and run:

```bash
read -rsp 'Agent key: ' CYBERSENTINEL_AGENT_KEY; echo
export CYBERSENTINEL_AGENT_KEY
cybersentinel-agent-watch \
  --input /path/to/nginx/access.log \
  --state /private/path/cybersentinel-agent.sqlite3 \
  --domain-id REPLACE_WITH_VERIFIED_DOMAIN_ID \
  --server https://ingest.your-domain.com \
  --allow-remote-host ingest.your-domain.com \
  --poll-seconds 1
```

Choose a new state file for each agent/domain/key. The watcher starts from the current end of the log unless `--from-start` is specified. Avoid `--from-start` on old production files: the current API rejects events older than 5 minutes.

## 14.4 External checks before accepting real telemetry

Do not paste keys into commands, screenshots or source control. From a machine outside the VPS, confirm:

```bash
curl -i https://ingest.your-domain.com/docs
curl -i https://ingest.your-domain.com/owner/register
curl -i https://ingest.your-domain.com/owner/health
curl -i https://ingest.your-domain.com/agent/v1/ingest
```

All four should be `404` because only **POST** `/agent/v1/ingest` is proxied. An unauthenticated POST to the exact path should be rejected, not return 200. Never run load testing against infrastructure you do not own or have permission to test.

Check service logs without logging Authorization headers or raw payloads; watch out for unexpected `429` and `503`. Backup the staging SQLite database regularly using SQLite's online backup API (not blind copies while active); keep backups encrypted and outside the Git repository. Test recovery before any actual use.

## Important constraints

- **Owner Portal is not public**. Self-service signup, hosted owner login and owner dashboard remain future steps.
- The agent now permits opt-in HTTPS to an explicitly configured hostname with standard certificate checks and redirects disabled. This is not mutual TLS, certificate pinning, or assurance of operator ownership.
- SQLite single-node staging has finite write throughput. A production multi-user service needs migrations, PostgreSQL, backed-up storage, rate limiting at the edge, resource monitoring, hardened authentication and incident response.
- A 5-minute API freshness window remains; a long outage causes queued data to become stale, requiring explicit operator intervention, not silent drops.
- No existing simulation or model metrics were upgraded. Detection still uses advisory rules, not the weak experimental Isolation Forest as a live blocking mechanism.
