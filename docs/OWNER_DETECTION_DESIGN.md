# CyberSentinel - Step 12 Detection Design

## Status and threat model

This is a localhost-only, user-consented security monitoring prototype. It is **not** an internet-facing SaaS, production IDS, malware scanner, or definitive proof of an intrusion. Alerts describe observed HTTP patterns that may merit investigation, including legitimate incidents and false positives.

An owner must sign in and DNS-verify a domain before provisioning an agent key. The Step 11 agent converts local NGINX JSONL into a strict minimal schema, removes raw IPs, paths, query strings, request bodies and headers, and replaces the source IP with a daily HMAC pseudonym. Step 12 operates **only** on those stored sanitized events. It does not load the historical Step 5 Isolation Forest, request raw logs from remote machines or send notifications externally.

## Ingestion and alert lifecycle

```
Local, owner-controlled NGINX JSONL
  -> one-shot cybersentinel-agent (minimized events)
  -> POST 127.0.0.1:8002/agent/v1/ingest
  -> verify domain-scoped agent key, bounds and timestamp
  -> atomic insert of nonduplicate events
  -> recompute only affected (domain, pseudonymous source, UTC minute) buckets
  -> upsert explainable rule alerts (unique per domain/source/minute/rule)
  -> GET /owner/domains/{domain_id}/alerts (owner bearer session)
  -> local Streamlit Owner Portal fragment refreshes every 10 seconds
  -> POST /owner/domains/{domain_id}/alerts/{alert_id}/acknowledge
```

No `simulation_run_id` is used. All windows are fixed UTC 60-second intervals derived from **event occurred_at**, not ingestion timestamps. A pseudonymous `source_ref` is an agent-produced value derived from the agent key and UTC day, which limits cross-day continuity and cannot reliably identify a real person or network host. Multiple clients behind proxies may be conflated; multiple keys for one domain do not necessarily produce the same pseudonym for the same client.

## Explicit, fixed rules (not ML)

| Rule ID | Severity | Condition within same domain, source and UTC 60-second window | Interpretation |
|---|---|---|---|
| `repeated_login_failures` | high | 5 or more HTTP 401 responses with `path_group=login` | Repeated failures, not necessarily password attacks |
| `http_404_burst` | medium | 8 or more HTTP 404 responses | Missing URLs, possibly reconnaissance or benign broken links |
| `server_error_burst` | medium | 5 or more HTTP 5xx responses | Availability, dependency or server fault |
| `request_volume_spike` | low | 40 or more requests | Relative local surge with arbitrary lab threshold |

These are deliberately simple initial heuristic thresholds. There is no confidence estimate, severity risk calibration, per-domain tuning, automated blocking, WAF enforcement, SMS/email or trusted attribution. HTTP 404 bursts are not equivalent to confirmed directory scanning. HTTP 401 responses may be generated by users who forgot their passwords. No ground-truth labels are inferred or saved as part of owner events.

## Data model

`detection_alerts` is stored in the owner SQLite database under ignored `simulations/runtime/owner/`. Each row includes domain, pseudonymous source, UTC minute, fixed rule, threshold, observed count, descriptive text, `open` or `acknowledged` status, and UTC epoch timestamps. There is a `UNIQUE(domain_id,source_ref,window_start,rule_id)` constraint. Ingestion and alert computation share the same write transaction, so one fails together with the other. Only **newly accepted** events can trigger evaluation; duplicates do not create new alerts. More accepted events can update an existing alert's observed count without reverting an acknowledgement.

The owner API requires a valid session and verifies the domain belongs to that owner before returning alerts or processing acknowledgements. A deleted domain cascades to its telemetry, agent keys and alerts. Alerts older than seven days by **window time** are purged opportunistically when new events are ingested; no scheduled cleanup exists yet. Retention is not a substitute for a real policy or background pruning in a hosted product.

## Performance and security boundaries

- Ingestion limits from Step 11 remain: maximum 25 events and 32 KiB per request, per-domain rate restrictions and +/-5-minute event timestamp checks.
- A single SQLite writer serializes local ingestion. No distributed queue, retries or high availability is available.
- Streamlit polls while an authenticated browser session is open. It does **not** monitor a website when the owner computer or agent is off.
- Owner credentials and the SQLite file never belong in Git or public Streamlit Cloud. Agent keys must only be retained in a local environment variable; the default client only permits `127.0.0.1:8002`.
- False positives and missed detections are expected. The previous Isolation Forest result (29.17% test attack recall on a controlled lab) is not used here and must not be represented as an operational score.

## Future hardening before public SaaS

Managed authentication with MFA and account recovery, PostgreSQL with tenant policies, audited API authorization, TLS, per-tenant rate budgets, reliable agent checkpoint/tailing, encryption at rest, worker queues, retry/dead-letter controls, secret rotation, retention and deletion service, observability, alert destinations, verification renewal, meaningful false-positive benchmarks and controlled attack/benign traces. No hosted owner registration or arbitrary remote targets are enabled by this step.
